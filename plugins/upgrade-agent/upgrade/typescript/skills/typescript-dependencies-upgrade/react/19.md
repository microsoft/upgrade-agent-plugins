# React 19 — breaking changes

The React 19 release removed several long-deprecated APIs and tightened TypeScript types. Most projects need a combination of codemod-driven and manual fixes. Follow the language-scoped commands and codemod safety gate in [react.md](../react.md). The official `react/19/migration-recipe` includes PropTypes-to-TypeScript conversion, so it is not safe to run across JavaScript or mixed-language source paths. Use the individual runtime transforms for JavaScript; preserve `.js`/`.jsx` and their existing JSDoc conventions rather than converting the project to TypeScript.

**Run the applicable codemods below unless the fast-path checkpoint in [react.md](../react.md) already passed.** Replace the source-path placeholders with inventoried paths, check the resolved CLI's `--help`, and apply the safety gate before running. Substitute `yarn dlx` / `pnpm dlx` for `npx --yes` per the project's package manager.

For **JavaScript source paths**, run the applicable runtime transforms individually, not the migration recipe:

```sh
npx --yes codemod@latest run react/19/replace-reactdom-render --target <javascriptSourcePath> --no-interactive --allow-dirty
npx --yes codemod@latest run react/19/replace-string-ref --target <javascriptSourcePath> --no-interactive --allow-dirty
npx --yes codemod@latest run react/19/replace-act-import --target <javascriptSourcePath> --no-interactive --allow-dirty
npx --yes codemod@latest run react/19/replace-use-form-state --target <javascriptSourcePath> --no-interactive --allow-dirty
```

For **TypeScript-only source paths**, run both the runtime migration recipe and the separate type-API migration:

```sh
npx --yes codemod@latest run react/19/migration-recipe --target <typescriptSourcePath> --no-interactive --allow-dirty
npx --yes types-react-codemod@latest preset-19 <typescriptSourcePath> --yes
```

For mixed-language projects, repeat the appropriate commands on separate JavaScript and TypeScript paths; never target the mixed directory with the recipe. Check parser failures, skipped files, imports, and repository build/lint/test results before claiming completion.

## Removed APIs

The migration recipe automates the `render`, `hydrate`, `unmountComponentAtNode`, and `act` import migrations when it recognizes the call shape. Verify the diff afterward, especially in files with dynamic call patterns.

- **`ReactDOM.render(element, container)` → `createRoot(container).render(element)`.** Import `createRoot` from `react-dom/client` (NOT `react-dom`). The old `ReactDOM.render` was deprecated in 18 and hard-removed in 19.
- **`ReactDOM.hydrate(element, container)` → `hydrateRoot(container, element)`.** Import `hydrateRoot` from `react-dom/client`. Same removal timeline as `render`.
- **`unmountComponentAtNode(container)` → `root.unmount()`.** You need to keep a reference to the root returned by `createRoot` to call `unmount()` on it. The codemod handles the simple case; for components that previously called `unmountComponentAtNode` from far away, you'll need to plumb the root reference through.
- **`ReactDOM.findDOMNode(component)` removed.** No automatic migration. Refactor to use refs (`useRef` / `createRef` / callback refs).
- **`act` no longer exported from `react-dom/test-utils`.** Import `act` from `'react'` directly. The codemod rewrites the import; verify your test setup.
- **`React.createFactory` removed.** Replace with JSX directly (`createFactory('button')` → `<button />`).
- **`react-test-renderer/shallow` removed.** If you use shallow rendering in tests, install `react-shallow-renderer` (a separate package that preserves the old API) or migrate tests to use `@testing-library/react` with full rendering.

### Render timing after root migration

[`root.render(...)` does not guarantee that the DOM and effects are ready before the next statement runs](https://react.dev/reference/react-dom/client/createRoot#root-render). After replacing `ReactDOM.render`, inspect bootstrap code that immediately queries rendered DOM or dispatches events consumed by component effects, including iframe initialization. Preserve the required initialization order rather than assuming the API replacement preserves synchronous readiness.

In tests, use the repository's existing async rendering/query helpers or [`await act(async () => { ... })`](https://react.dev/reference/react/act) before asserting on the resulting UI; do not put `act` in production code, add arbitrary sleeps, or weaken assertions. Rerun the full existing package test suite after focused checks: a flow passing alone does not establish that initialization and cleanup still work across the suite.

## Removed component patterns

These require migration. The recipe handles string refs; refactor the other patterns manually.

- **String refs (`ref="myRef"` and `this.refs.myRef`) removed.** Convert to callback refs or `createRef` / `useRef` with the recipe's `replace-string-ref` codemod.
- **Legacy context (`childContextTypes`, `contextTypes`, `getChildContext`) removed.** Migrate to `React.createContext`.
- **Module-pattern components (functions returning `{ render() }`) no longer supported.** Convert to a regular function component returning JSX.
- **`PropTypes` and `defaultProps` on function components are runtime no-ops.** They no longer emit dev warnings either. Migrate to TypeScript types or default parameters. Class components still support `defaultProps`.

## JSX & ref-as-prop changes

- **`ref` is now a regular prop** for function components. You no longer need `forwardRef` for new components — accept `ref` directly in props. Existing `forwardRef` calls still work and don't need to be migrated.
- **Modern JSX transform is mandatory.** Update `tsconfig.json` `"jsx": "react-jsx"` (or `"react-jsxdev"` in development) and remove `import React from 'react'` from files that only use JSX (no React API). Babel users: update `@babel/preset-react` to `{ runtime: 'automatic' }`.

## TypeScript-specific changes

These often manifest as compile errors after the version bump. The `react/19/migration-recipe` does **not** perform the React type-API migration. Run the dedicated TS codemod separately on inventoried TypeScript source paths: `npx --yes types-react-codemod@latest preset-19 <typescriptSourcePath> --yes` (substitute `yarn dlx` / `pnpm dlx` for `npx --yes`). Do not use `--no-interactive` or `--allow-dirty` with this tool. Review its selected transforms and generated imports; parser errors or skipped applicable files require a supported parser retry or a verified manual migration, not a success claim. Prefer explicit prop shapes over the `react-element-default-any-props` transform's `any` fallback. Apply the full safety gate in [react.md](../react.md), including repository import-order/format checks before a hook or install runs. Items the TS codemod can't infer are listed below and need manual fixes.

- **`ReactElement` default prop type changed from `any` to `unknown`.** Generic code that relied on the `any` default may now fail to compile. Annotate explicitly: `ReactElement<MyPropsType>` or `ReactElement<unknown>`.
- **The global `JSX` namespace was removed in favor of `React.JSX`.** References to `JSX.IntrinsicElements` etc. should become `React.JSX.IntrinsicElements`. The `types-react-codemod` preset-19 handles this.
- **`useRef` now requires an initial value.** `useRef<HTMLDivElement>()` (no argument) is a compile error — use `useRef<HTMLDivElement>(null)`.
- **Ref callbacks may return only a cleanup function or nothing.** Assignment expressions such as `ref={current => (instance = current)}` implicitly return the assigned value and are rejected by the React 19 types. Use a block body such as `ref={current => { instance = current; }}`; the preset's `no-implicit-ref-callback-return` transform handles this pattern.
- **`useReducer` type arguments changed.** Prefer contextual inference with `useReducer(reducer)`. When explicit types are required, provide the state type and the action type in a tuple rather than passing the full reducer type.
- **`useCallback`/`useMemo` callbacks inferring `any` parameters more strictly.** Add explicit parameter types where TypeScript can no longer infer them.
- **`Component<P, S>` second-argument default tightened.** Class components without explicit state types may need `Component<P, {}>`.
- **`TS2304: Cannot find name 'Iterable'` / `TS2456: Type alias 'ReactNode' circularly references itself`.** `@types/react@19`'s `ReactNode` references the `Iterable` lib type. These fire when the project's `tsconfig` `lib`/`target` is too old to include it, or when a nested `tsconfig.json` doesn't `extend` the root and so misses the lib / `skipLibCheck` settings. Fix by raising `lib` (e.g. add `"ES2015"`/`"ES2020"`) and/or setting `"skipLibCheck": true` on the offending tsconfig — and make sure nested configs `extend` the root.
- **`TS2717: Subsequent property declarations must have the same type ... 'SVGProps'` (or other duplicate-identifier errors on React types).** Two different copies of `@types/react` are resolved in the tree. Bump `@types/react` and `@types/react-dom` **together** to the same 19.x line and dedupe (`npm dedupe`, or clear stale lockfile entries) so only one copy remains.

## Ecosystem peer-dep churn

These are the libraries most likely to need a coordinated bump alongside React 19. If `typescript_install_dependencies` reports peer-dep errors after the React bump, check these first:

- **`@testing-library/react` requires v15 or later for React 19** (v16+ recommended). v12-v14 will fail to install.
- **`@types/react` and `@types/react-dom`** must be in the 19.x line. The exact published version may lag React itself by days — query `npm view @types/react version` rather than assuming a number.
- **`react-router` / `react-router-dom`** generally support React 19 from v6.28+ and v7+.
- **`react-redux`** requires v9+ for React 19.
- **`@reduxjs/toolkit`** v2+ for React 19 (compatibility comes via `react-redux` v9).
- **State libraries (`zustand`, `jotai`, `valtio`, etc.)** — generally support React 19 in their latest majors. Upgrade together with React.

## Strict-mode and concurrent rendering reminders

React 19 changes development Strict Mode behavior: `useMemo` and `useCallback` reuse the memoized results from the first render during the second render, and ref callback functions are double-invoked on initial mount to simulate replacement by a Suspense fallback. Components must keep ref setup and cleanup resilient to re-initialization. If you're also migrating from React 17, see [react/18.md](./18.md) for the React 18 strict-mode notes.
