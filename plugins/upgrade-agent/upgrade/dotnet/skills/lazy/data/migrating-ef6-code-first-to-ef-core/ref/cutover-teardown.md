# Full Cutover: Retiring EF6 Artifacts

> **Load this file only after the user has explicitly confirmed a full cutover.**
>
> A full cutover means the .NET Framework host is **retired** — not merely upgraded,
> not "about to be", and not running in parallel. If any other application, job, or tool
> still runs EF6 against this database, stop and use the
> `managing-shared-database-schema` skill instead.

## Confirmation gate

Before running anything in this file, confirm all four with the user:

- [ ] The .NET Framework host that used EF6 is **decommissioned** or will be as part of this change
- [ ] No other application, background job, admin tool, or scheduled task uses the EF6 `DbContext`
- [ ] The EF Core baseline migration is created, **reviewed against the schema that already
      exists**, and registered in `__EFMigrationsHistory` without being executed
- [ ] A database backup exists and restore has been tested

If the project is in a side-by-side window — both hosts live against one database — **none of
this applies**. The EF6 migration assets remain the authoritative schema ledger and deleting
them destroys the ability to deploy further schema changes from the host that still owns them.

## Retiring the EF6 migration assets

Once the gate above passes:

1. Confirm all EF6 migrations have been applied to every environment — dev, test, staging,
   production. An unapplied migration lost here cannot be recovered from source.
2. **Check where the EF Core baseline was scaffolded first.** EF Core's default output
   directory is *also* `Migrations/`, so a baseline created with default settings lands in the
   very folder you are about to delete — and deleting it destroys the snapshot and migration
   you just created. Scaffold it into a sibling folder
   (`dotnet ef migrations add InitialCreate --output-dir EFCoreMigrations`) or verify it lives
   in a different project before continuing. A *subfolder* of `Migrations/` is not sufficient:
   it shares the fate of its parent here, and Step 2 of the main skill excludes it from
   compilation via the recursive `Migrations\**` glob.
3. Delete the EF6 migration files **by inventory, not by folder**: each `DbMigration` subclass
   generated by `Add-Migration` (the `.cs` / `.Designer.cs` / `.resx` triple) plus the
   `Configuration` class generated by `Enable-Migrations`. Removing an undifferentiated
   `Migrations/` folder is what takes the EF Core ledger with it.
4. Delete the EF6 `Configuration` class if it lives outside `Migrations/`.
5. Leave `dbo.__MigrationHistory` **in the database**. It is small, it is the only record of
   what EF6 applied, and dropping it removes the audit trail. It does not interfere with
   EF Core, which uses `dbo.__EFMigrationsHistory`.

**Prefer operator-performed deletion.** Present the list of files to remove and let the user
delete them, or confirm explicitly before doing it. These files are the schema ledger; their
removal is not reversible from the application's perspective.

## Full-cutover success criteria

Apply these **only** after a confirmed full cutover:

- EF6 migration files removed (`DbMigration` classes and `Configuration`), with the EF Core
  baseline verified still present
- EF6 `Configuration` class removed
- No `System.Data.Entity` namespaces remain
- `EntityFramework` package reference removed
- `dbo.__MigrationHistory` retained in the database as a historical record
