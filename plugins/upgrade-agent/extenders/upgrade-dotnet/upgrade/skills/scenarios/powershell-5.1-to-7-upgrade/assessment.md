# Stage 1: Assessment

Inventory every PowerShell 5.1 → 7.x blocker across the scoped scripts and record it
in `assessment.md`.

## Entry Criteria

- Pre-initialization complete (script scope, `targetPowerShellVersion`, and platform
  intent confirmed).
- `initialize_scenario` already called — working folder exists at
  `.github/upgrades/{scenarioId}/`.
- If git repo: on the correct working branch.

## Exit Criteria

- `assessment.md` created in the workflow folder, with `scan-findings.csv` beside it.
- Every pinned module classified Native, Shimmed, or Blocked, and the resolved pin
  recorded for planning.
- **Guided mode**: user has reviewed and approved the assessment.
- **Automatic mode**: assessment summary surfaced to the user; proceed to planning
  immediately.

## Steps

### Step 1 — Confirm the PowerShell host and analyzer

Stage 0 established these as prerequisites. Re-confirm rather than re-litigate,
because the scan runs under PowerShell itself and the primary gate needs the
analyzer:

```powershell
Get-Command pwsh, powershell -ErrorAction SilentlyContinue |
    Select-Object Name, Version, Source
Get-Module -ListAvailable PSScriptAnalyzer |
    Sort-Object Version -Descending | Select-Object -First 1 Name, Version
```

- Both present → proceed. `pwsh` is the target engine, so its verdict is the one
  that matters, and the compatibility profile is generated by reflecting over it.
- **Either missing → stop.** Report which one, give the install command from the
  scenario SKILL.md Step 0, and wait. Do not assess under 5.1, do not run the
  sidecar alone, and do not substitute a `Select-String` sweep — none of those is
  an assessment, and presenting one as an inventory is the specific failure this
  scenario exists to prevent.

There is no degraded mode here by design. Without `pwsh` no compatibility profile
can be generated, so removed commands, parameters and types — the bulk of the real
work — are invisible, and the scan returns a short list that reads like a small
migration. Without PSScriptAnalyzer the primary detector does not exist at all.
Either way the output is confidently clean in the one direction that matters, and
a user who plans against it discovers the blockers in production.

Report the host and the analyzer version. The host determines scan fidelity
(Step 4) *and* what the generated profile describes; the analyzer determines
whether the primary detector exists at all.

### Step 2 — Collect organisation knowledge

Before scanning, gather anything the shipped catalog cannot know: internal
snap-ins, in-house modules, and the map from each to its replacement. Two
sources, most specific last:

1. **Contribution skills.** Check **Available Skills** for any whose description
   declares `provides: powershell-compatibility-rules`. Load each and read its
   `## Snapin Module Map` table (and any `## Compatibility Rules` block).
2. **What the user has already told you.** If the user stated a mapping in
   conversation — "`Contoso.Foo.Snapin` is `ContosoFoo` now", "that one has no
   PS7 replacement" — treat it as a contribution. It does not need to be a
   skill. If it contradicts a contribution skill, the user wins; say so and name
   the skill you overrode.

Project everything collected into
`.github/upgrades/{scenarioId}/contributed-rules.psd1`. The
`scanning-powershell-compatibility` skill documents the exact rule shape to
emit, including how to represent "no replacement exists".

Project it — do not merely remember it. Knowledge that stays in the conversation
changes how you remediate but not what the scan reports, so the CSV, the
assessment counts, and the execution re-scan baseline would all disagree with
what the user just told you.

If there is nothing from either source, skip this step and drop
`-AdditionalRulesPath` below. Say so in the assessment — it tells the reader that
every internal snap-in will appear as a generic blocker with no named
replacement, which is the single most useful thing a customer can fix about
their own scan.

### Step 2a — Confirm the pinned modules load natively under PowerShell 7

Do this **before** generating the profile. The profile is built over whatever
modules are installed, so a pin that has to change later invalidates it and
every finding measured against it.

Take the `requiredModules` from Stage 0 Step 0b and classify each pinned version
into one of three outcomes. **Probe one module per fresh `pwsh` process** — the
compatibility session is created once and then persists, so several imports in
one session all look alike and the signal stops being per-module:

```powershell
# Per module. Fresh process each time.
pwsh -NoProfile -Command "try { Import-Module <Name> -RequiredVersion <Version> -ErrorAction Stop } catch { 'Blocked'; exit }; if (Get-PSSession -Name WinPSCompatSession -ErrorAction SilentlyContinue) { 'Shimmed' } else { 'Native' }"
```

- **Native** — loads in-process. Nothing to do.
- **Shimmed** — loaded through the Windows PowerShell compatibility layer. It
  works, but every object crossing the boundary is deserialized: methods are
  gone and only properties survive. Treat as migration work, not as passing.
- **Blocked** — refuses to load. Any script importing it cannot run on
  PowerShell 7 at the current pin.

**Do not classify by whether `Import-Module` threw.** A shimmed module imports
successfully and reports itself as loaded. Do not "fix" one with
`-SkipEditionCheck` either — that suppresses the check, not the incompatibility.

For every module that is not **Native**, look for a newer version that is. The
usual publishing pattern keeps the module name and raises the major version, so
the replacement is found by version, never by name:

```powershell
Find-Module -Name <Name> -AllVersions |
    Where-Object { $_.Tags -contains 'PSEdition_Core' } |
    Sort-Object { [version]($_.Version -replace '-.*$') } |
    Select-Object -First 1
```

Report the current pin, the lowest version that supports PowerShell 7, and
whether reaching it crosses a major — a major bump carries breaking changes and
is its own task, not a version-string edit.

**A missing `PSEdition_Core` tag does not mean the module is Windows-only.** The
tag is optional and many genuinely cross-platform modules omit it; the
authoritative `CompatiblePSEditions` field is not published by the gallery at
all. So the tag is usable as evidence *for* compatibility and as a shortlist of
candidates, never as proof *against* it. Confirm a candidate by probing it the
same way above before recommending it. Where no tagged version exists, probe the
latest release before concluding anything.

If no version loads natively, say so plainly — that is a **Blocker** for every
script importing it, and it belongs in the assessment rather than being
discovered halfway through execution.

Record the pin you land on. That is what Step 3 builds the profile over and what
execution updates the manifest and bootstrap to match.

One caution before recommending any bump: the same publishing pattern that adds
PowerShell 7 support usually **drops 5.1** in the same major. For files that
planning marks 5.1-compatible because callers still on 5.1 dot-source them,
raising the pin is a one-way move and follows the bi-compatible rules rather
than being applied on its own.

### Step 3 — Generate and validate the compatibility profile

Load the **`scanning-powershell-compatibility`** skill. Before any detection
runs, build the profile that PSScriptAnalyzer will analyse against:

```powershell
pwsh -NoProfile -File <skill>/scripts/New-PSSACompatibilityProfile.ps1 -OutputPath .github/upgrades/{scenarioId}/target-profile.json -TargetPlatform <the platform confirmed in Stage 0 Step 3> -TargetPSVersion <the target version confirmed in Stage 0 Step 2> -RequiredModule <the requiredModules confirmed in Stage 0 Step 0b>
```

**Run this under the `pwsh` the user is actually migrating to.** The profile is
built by reflecting over the running interpreter, so the version of `pwsh` on
`PATH` — not the version agreed in Stage 0 — is what silently defines the
result. `-TargetPSVersion` does not change the profile; it makes the mismatch
audible. Generating on a host *newer* than the target inventories everything
added since as available and suppresses its findings, so code can pass the
rescan and still fail in production. The script warns in that direction only;
the reverse (host older than target) can only over-report and is safe.

**Do not skip this and use the profiles PSScriptAnalyzer
ships.** They stop at PowerShell 7.0.0, were built on an unrelated machine, and
carry that machine's module versions — a stale in-box Pester alone can generate
thousands of phantom findings.

Read `target-profile.validation.json` before going further. The status is
computed so that **every under-reporting condition is `FAIL`** — `WARN` is
reserved for conditions that can only produce extra findings, never hide them:

- `FAIL` → the profile will report **false passes**. Do not analyse against it.
  Fix the cause and regenerate. It is raised by any of: contamination (the
  session had the Windows PowerShell compatibility shims loaded), a module
  version newer than the pin reaching the profile, a platform mismatch between
  the generating host and the target, or a host newer than the target version.
  The console output names which one.
- `WARN` → usable. Copy `MissingCommands` and `MissingTypes` into the assessment
  as the **known false-positive ledger** for this run. Every finding naming one
  of those is an artifact of profile generation, not a blocker.
- `PASS` → proceed.

The result object is nested under `.Validation` in that file. Reading
`.Status` off the root returns `$null`, which compares unequal to `'FAIL'` and
lets a contaminated profile through — use `.Validation.Status`.

Record the profile path, its validation status, and the ledger. Planning and
execution both need them, and a later re-scan that uses a *different* profile is
not comparable to this one.

### Step 3a — Run PSScriptAnalyzer (primary detection)

Run the wrapper, not `Invoke-ScriptAnalyzer` directly:

```powershell
pwsh -NoProfile -File <skill>/scripts/Invoke-PSSACompatibilityScan.ps1 -Path <scope-root> -ProfilePath .github/upgrades/{scenarioId}/target-profile.json -TargetPSVersion {targetPowerShellVersion} -OutputPath .github/upgrades/{scenarioId}/pssa-findings.json
```

A direct `Invoke-ScriptAnalyzer` call has four traps, and **three of them fail by
reporting a clean estate** rather than by erroring — so hand-rolling the call
risks reporting a false pass on primary detection. The wrapper closes all four:
it resolves the profile to an absolute path (a bare name is resolved against
PSScriptAnalyzer's own bundled profile folder, not your working directory, and
yields `findings=0 errors=1`); passes `-IncludeRule`, without which the whole
default rule set also fires and style findings inflate the compatibility
inventory; sets `Enable = $true` per rule, without which the rule checks nothing;
and carries the full file path, since `DiagnosticRecord.ScriptName` is the leaf
filename only.

It also fails loudly where a hand-rolled call would not: it stops if the profile
is missing or its validation status is `FAIL`, and it tracks files the analyzer
could not process. A file that errored contributed zero findings *without being
analyzed*, which is not the same as being clean — the run reports
`coverage : INCOMPLETE` and exits non-zero. Treat any `INCOMPLETE` as an
unfinished scan, not a result.

Budget several minutes on a large estate. Add `-OutputFormat Both` if you also
want the CSV.

Parse errors emitted during this pass (for example
`WorkflowNotSupportedInPowerShellCore`) are **hard blockers, not noise**. Keep
them in their own section of the assessment; they cannot be edited around.

### Step 3b — Run the sidecar scan

The sidecar covers what PSScriptAnalyzer is structurally unable to see —
encoding and other behavioral changes, parameter values, type accelerators,
module availability, COM, deprecated-but-present cmdlets — and carries the
severity and `Skill` routing metadata for everything, including the
PSScriptAnalyzer findings:

```powershell
pwsh -NoProfile -File <skill>/scripts/Get-PSCompatibilityScan.ps1 -Path <scope-root> -AdditionalRulesPath .github/upgrades/{scenarioId}/contributed-rules.psd1 -OutputPath .github/upgrades/{scenarioId}/scan-findings.csv
```

CSV is the canonical sidecar artifact — planning and execution both query it by
`RuleId` and `File`. Pass `-OutputFormat Both` if you also want a JSON envelope
(useful when a downstream tool needs the run metadata rather than just the rows).

The scanner parses each script with the real PowerShell parser and applies the
declarative rule catalog in the skill. Comments, comment-based help, and string
literals are excluded structurally, so `.EXAMPLE  Get-WmiObject ...` in a help
block does not become a finding.

Its summary reports how many contributed rules were added and which shipped
rules they overrode. Carry those numbers into the assessment: a scan run with
org rules and one run without are different scans, and the difference must be
visible to whoever reads the result.

`-Path` accepts **files as well as directories**, so under partial scope pass the
closed selection directly rather than scanning the whole estate. If you do scan
a wider root, every count you report must be filtered to the selection
(`scan-findings.csv` is keyed by `File`). Do not present estate-wide totals as if
they were the job.

Do **not** hand-roll a parallel inventory with `grep` or `Select-String`. A
line-based search cannot tell code from comments, cannot resolve parameter
prefixes (`-Enc Byte` *is* `-Encoding Byte`), and cannot see that a splatted call
hides its parameter set. Each of those is a false positive that becomes a
must-remediate item on someone's plan. The scanner output is also the baseline
that execution re-scans against, so it must be reproducible.

If the user has organisation-specific blockers (an internal module that will not
survive the move, a deprecated in-house cmdlet), extend the catalog rather than
adding a second detection mechanism — see *Extending the catalog* in the skill.

### Step 3c — Combine, and be honest about precision

The two result sets do not duplicate each other at the rule level. Any rule
PSScriptAnalyzer covers is knowledge-only in the catalog: it does
not run, and the sidecar cannot emit it. The sidecar reports only what PSSA
misses.

One deliberate exception exists at the *site* level. A catalog rule may overlay a
more specific answer on a generic analyzer finding: `Add-PSSnapin
Microsoft.Exchange...` is reported by PSSA as the generic `snapin` Blocker, and
the sidecar adds `exchange-snapin`, which names the snap-in and gives the
Exchange-specific remediation. That is one site with two findings, not two sites.
Count it once; plan from the specific one. `exchange-snapin` is currently the only
rule that does this — it is the only one carrying `Supersedes`.

What the catalog still contributes to a PSSA finding arrives already attached.
`Invoke-PSSACompatibilityScan.ps1` joins on the analyzer's structured `Command`
and `Parameter` properties and stamps `CatalogRuleId`, `Category`,
`CatalogSeverity`, `Skill` and `Remediation` onto each row.

**Group and order by `CatalogSeverity`, not `Severity`.** PSSA's own `Severity`
is `Warning` for every compatibility finding it emits, so it carries no signal.

```powershell
$pssa = (Get-Content .github/upgrades/{scenarioId}/pssa-findings.json -Raw | ConvertFrom-Json)
$pssa.findings | Group-Object CatalogSeverity | Sort-Object Name
$pssa.counts.unenriched    # findings with no catalog entry -- real, but undescribed
```

A non-zero `unenriched` count is not noise to discard. Those are commands PSSA is
confident are unavailable that the catalog has nothing to say about; they belong
in the report with the replacement worked out from the target host. Say how many
there are rather than letting them disappear into an ungrouped bucket.

Two classes of PSScriptAnalyzer finding are known artifacts of how the rule
works, not blockers, and must be marked as such rather than dropped silently:

| Class | Looks like | Why |
|---|---|---|
| Unresolved local function | `The command 'Write-Log' is not available…` where the estate defines `Write-Log` | The rule has no symbol table and does not follow dot-sourcing |
| Abbreviated parameter | `The parameter 'fore' is not available for command 'Write-Host'` | The rule checks name equality and [does not emulate parameter binding][pssa-cmds] |

[pssa-cmds]: https://github.com/PowerShell/PSScriptAnalyzer/blob/main/Rules/CompatibilityRules/UseCompatibleCommands.cs

Add both to the false-positive ledger started in Step 3, alongside the profile's
`MissingCommands`/`MissingTypes` — the wrapper already copies those into
`pssa-findings.json` under `falsePositiveLedger`, so extend that rather than
starting a second list. Execution reads the ledger, so anything left out of it
will be worked as if it were real.

State plainly in the assessment that this is static analysis: it over-reports in
the classes above, and it cannot see runtime-only behavior at all. The scan is a
starting inventory, not a proof of correctness.

### Ask for the snap-in mappings the scan could not resolve

Do not expect the user to have supplied every mapping in Step 2 — they do not
know which snap-ins are in the estate until the scan says so.

If the findings include generic `snapin` rows, pull the distinct snap-in names
from their `Snippet` column and put that list to the user. Ask for a replacement
module, or an explicit "no replacement", for each. This is the one question in
the assessment where the user holds information you cannot derive, and the list
is short and concrete rather than an open-ended request for "any org knowledge".

Not every `snapin` row names a snap-in. `Get-PSSnapin -Registered` is a query,
not a load, and `Snippet` is capped at 200 characters so a deeply-indented call
can be cut off. Extract only names you can actually see, and never present a
parameter such as `-Registered` as if it were a snap-in. If a row yields no
name, leave it out of the question rather than guessing.

If they answer, project the answers into `contributed-rules.psd1` and re-run the
scan so the findings carry specific rule ids and named remediations. If they
decline, or there were no generic `snapin` findings, do not re-run — a re-scan
that changes nothing is pure cost on a large estate.

Then offer, once, to save the mappings as a
`provides: powershell-compatibility-rules` skill so the next repo and the next
run inherit them. Offer; do not insist.

### Step 4 — Check scan fidelity

The scanner prints how many files it could not fully parse, with the parse error
for each, and marks their findings `Fidelity = Tokens`.

- **`workflow` files.** PowerShell 7 refuses to parse `workflow` at all. These
  are still scanned from the token stream — commands, keywords, types, modules
  and member names are all found — but the rules that need a real syntax tree
  are skipped, including `com-object` and the encoding rules. The scanner prints
  the exact rule IDs it skipped; treat a clean result for those as *not checked*,
  not *not present*. The scan counts these as coverage gaps and exits non-zero,
  so this step cannot be skipped by reading the exit code alone. Re-run just
  those paths under
  `powershell` (5.1), which parses workflows, to bring them to `Full` fidelity.
- **Genuinely malformed scripts.** A file that parses under neither host is
  broken *today*. Report it as a finding in its own right — it is not a
  migration blocker, it is a pre-existing bug, and it must not be silently
  counted as clean.

### Step 5 — Read the summary, not the CSV

Read the scanner's printed summary. The `scan-findings.csv` written beside
`assessment.md` is a **lookup table, not reading material** — on a large repo it is
tens of thousands of rows and will blow out the context window. Its columns are:

`File,Line,RuleId,Category,Severity,Fidelity,DetectedBy,Snippet`

(`DetectedBy` is `catalog` on every row — the sidecar runs only rules PSSA does
not cover. It is kept so the column schema stays stable.)

Query it per file or per rule id (`Import-Csv | Where-Object`) when you reach that
item in the execution loop; never read it whole. Remediation text is **not** in
the CSV: it is per-rule and joined on `RuleId` against the rule catalogs.

That join is against the shipped catalog **and**
`.github/upgrades/{scenarioId}/contributed-rules.psd1`. A contributed rule id
resolves only from the contributed catalog, so keep that file for the life of
the operation and consult it in planning and execution as well. Deleting it, or
joining against the shipped catalog alone, turns every contributed finding into
an unknown rule id with no remediation and no `Skill:` routing — the failure
appears two stages after the mistake.

### Step 6 — Note coverage gaps

The sidecar scan prints a `coverage :` line. `complete` means every scoped path
was enumerated **and** parsed; `INCOMPLETE` names what was lost — unreadable
directories, missing input paths, files that did not parse, or a mix. Unreadable
directories and missing paths are listed in a **COVERAGE GAPS** block; files that
did not parse are listed in the fidelity block above it (Step 4). An unreadable
directory costs the *entire subtree* — its files and all its sub-directories — so
zero findings under it means "not looked at", never "clean".

`INCOMPLETE` also means the scan exited non-zero, so a task gate that reads the
exit code and a human reading the summary reach the same conclusion.

If any scoped path was unreadable, or the scan skipped a directory the user
expected to be covered, the scan is **partial**. Record that in the assessment and
carry it into the plan — do not claim coverage for those paths. Re-run those
paths from a session that can read them rather than accepting the gap.

### Step 7 — Map the dot-source graph

Scripts frequently `. .\CommonLibrary.ps1`. Before planning, identify the shared
libraries that multiple scripts dot-source: one library fix ripples across every
caller, and it changes task ordering (libraries before callers). A quick search for
`^\s*\.\s+` across the scope is enough to spot the hubs.

**Under partial scope this step is not just ordering — it defines the work.** Walk
the dot-source edges out of the selection *transitively* and add every library it
reaches; a selected script is not migrated while a library it loads still calls
`Get-WmiObject`. Then walk the edges back **in**: for each library you just pulled
in, find its callers that are *not* in the selection. Those files stay on 5.1 and
constrain how the library may be rewritten
([planning.md](planning.md) Step 2). Report both sets — the closed selection, and
the shared files with out-of-scope callers.

Dot-sourcing is resolved at runtime, so a computed path (`. $libDir\x.ps1`) cannot
be followed statically. Flag those as unresolved rather than assuming the selection
is closed.

## Presenting the Assessment

Summarize for the user:
- The host the scan ran under, and the scan's fidelity (how many files were
  degraded, and why).
- Scripts scanned, scripts with findings, and any skipped paths.
- Finding counts by severity (see the Blocker Severity Model in `SKILL.md`).
- The handful of highest-volume rule ids, and which are architectural
  (snap-ins, Exchange, workflow) vs mechanical.
- Shared libraries that many scripts depend on.

Keep `Advisory` findings out of the blocker narrative. The six encoding rules in
particular fire on a large fraction of any real estate. Report them as counts and
an optional batch, not as migration work, and keep them split:
`outfile-output-encoding` (`Out-File`), `clixml-output-encoding` (`Export-Clixml`),
`tee-output-encoding` (`Tee-Object -FilePath`) and `redirection-output-encoding`
(`>`/`>>`) change the bytes of **every** file including pure ASCII, while
`ansi-output-encoding` and `csv-output-encoding` change only non-ASCII. Only the
first group survives the "our data is all ASCII" objection, so collapsing them
into one number makes the report less actionable, not more.

Under partial scope also state: the files the user named, the files closure added
and why, any unresolved (computed-path) dot-sources, and which files are shared with
callers left on 5.1.

Then transition per flow mode:
- **Guided mode**: wait for approval before planning.
- **Automatic mode**: proceed to planning immediately.
